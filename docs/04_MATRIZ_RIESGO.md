# Fase J | Matriz de riesgo

| Cambio candidato | Probabilidad de romper | Impacto si rompe | Riesgo | Cómo reducirlo |
|---|---|---|---|---|
| Extraer clase de notificación | Media — hay que mover dos `println` fuera de `procesar()` y decidir cómo se invoca el colaborador nuevo; fácil de olvidar una llamada o cambiar el orden respecto a `confirmar()`. | Medio — si el orden entre "guardar", "notificar" y "confirmar" cambia, el mensaje de consola podría imprimirse antes/después de lo esperado, o duplicarse. No afecta el monto cobrado. | **Medio** | Caracterizar primero el orden exacto de las tres acciones (persistir → notificar → confirmar) con una prueba que capture la secuencia de salida, y extraer sin alterar ese orden. |
| Introducir Correo | Media — implica cambiar el tipo de un campo de `Reserva` (de `String` a `Correo`), lo que toca el constructor y todos los puntos que lo invocan (incluido `Main`). | Alto — si el Value Object valida en su constructor y se construye antes de llegar a `ServicioReservas`, un correo inválido pasaría de "silenciosamente rechazado con retorno 0" a "excepción en la construcción de `Reserva`", lo cual **sí cambiaría el comportamiento observable**. | **Alto** | Definir explícitamente si `Correo` debe validar en su propio constructor (cambio de contrato) o permitir valores inválidos y dejar la validación en `ServicioReservas` (cambio interno seguro). Probar ambos casos límite (LB-03) antes y después. |
| Introducir PeriodoReserva | Media — mismo tipo de cambio que `Correo`: agrupa `inicio`/`fin` en un objeto nuevo que reemplaza dos campos en `Reserva`. | Alto — igual que arriba: si `PeriodoReserva` valida `fin > inicio` en su constructor, un periodo inválido pasaría de "retorno 0" a "excepción al construir la reserva", rompiendo el escenario LB-04 tal como se observa hoy. | **Alto** | Decidir en el plan si la validación de periodo se mueve al Value Object (cambio de contrato, requiere ajustar `Main` y cualquier otro llamador) o se mantiene como chequeo en `ServicioReservas` sobre el nuevo objeto (cambio interno, más seguro para este momento). |
| Simplificar validaciones | Alta — reordenar o fusionar los cuatro `if` es el tipo de cambio más tentador y más fácil de hacer mal, porque las guard clauses actuales son independientes entre sí y el orden en que se evalúan determina, para una entrada con múltiples fallas simultáneas, cuál validación "gana". | Alto — el código actual no distingue la causa del rechazo (todas retornan `0`), pero *si* alguna vez se agrega esa distinción, invertir el orden de los `if` cambiaría qué motivo se reporta primero para una `Reserva` con varios problemas a la vez. | **Alto** | Antes de tocar el orden, escribir una prueba de caracterización por cada validación de forma aislada (una sola condición inválida a la vez) y, si se prueban combinaciones, documentar cuál gana hoy antes de reordenar. |
| Separar cálculo VIP | Baja — es la extracción más contenida: el cálculo (`40`, `× 0.85` si VIP) no depende de ningún otro campo ni tiene efectos colaterales, solo lee `r.getTipo()`. | Bajo — un error de extracción se detecta de inmediato comparando el monto retornado (`40.0` o `34.0`) contra el valor esperado; no hay mensajes de consola ni cambios de estado involucrados. | **Bajo** | Extraer primero este cálculo (es el candidato de menor riesgo), respaldado por `vipConservaResultadoActual()` para NORMAL y VIP antes y después del cambio. |

## Escala

- **Bajo:** cambio local, comportamiento bien entendido y prueba fácil de crear.
- **Medio:** afecta varias decisiones o requiere adaptar construcción de objetos.
- **Alto:** puede alterar contrato observable, flujos de error o efectos externos.
